Frontend and backend, in parallel

Principles for how Qred builds APIs, and the decisions they led to in the card overview Screen.

Nazim Huseynov · Node.js Backend Developer case

The talk is Task 1: how to fix the collaboration problems. Task 2, the implementation, shows up as evidence that each principle works in practice. Implementation details are in an appendix for questions.

Three root causes behind the symptoms

The API is defined late

It takes shape while the backend is being built, so the frontend learns the real shape at integration.

"API definition and implementation sometimes occur too late."

Expertise is a bottleneck

Few people can specify an API well. PMs cannot, and less experienced developers need the details spelled out.

"Technical competence to specify … is a scarce resource."

Frontend waits on backend

Competent frontend developers sit idle or build against guesses until a real endpoint exists.

"Frustrated by delays in API availability."

Fix the first and the other two get cheaper: agree the API before anyone builds it, then let tooling carry the expertise.

The case lists seven bullets; they collapse into these three. The order matters: a late definition is what makes expertise scarce (every API is a bespoke negotiation) and what blocks frontend.

Move the contract to the start of the work

The contract is an OpenAPI file with examples taken from the design. It is reviewed like code and merged before either side builds.

This is the whole proposal in one picture. The next slides are the principles that make it work, each with the decision it leads to and where the case implementation shows it.

Principle 1

The contract is the first deliverable

The ask

"The API definition and implementation sometimes occur too late in the software development lifecycle."

The decision

  • An OpenAPI contract with examples is written and merged before either side builds.
  • "Contract merged" is part of the Definition of Ready for any story that needs an API.
  • Everything else is derived from it, so it can't drift from the code.

In the case Each of the four services has a contract in contracts/, and its routes and request validation are built from that file.

One source of truth, many outputs. If the contract is the thing you merge first, everything downstream (mocks, types, tests) exists from day one and cannot silently diverge.

Principle 2

Design around Screens, in shared language

The ask

"Product Managers only have limited technical knowledge and require assistance in describing the technical implementation details."

The decision

  • The PM writes a Screen brief: its sections, the data and states of each, and the actions on it.
  • One endpoint per Screen, with examples that read like the wireframe, so a PM can check them.
  • A glossary fixes the words, so PM, frontend and backend mean the same thing.

Principle 3

Never block the frontend

The ask

"The Frontend Developers are competent and can be frustrated by delays in API availability."

The decision

  • A mock generated from the contract is running the day the contract merges.
  • The app always calls the real BFF, which switches each upstream from mock to real behind a flag. No app release is needed.
  • Fail safe: an unknown flag means real, and production never allows mocks.

In the case A mock per contract, a flag per upstream, and a Qred-Data-Sources header naming what served each response.

ADR 0004. Mobile releases are slow, so switching belongs on the server. Switching per upstream rather than per Screen means a half-built backend is still useful: Card can be real while Billing is still a mock. Real data can roll out to testers before everyone.

Principle 4

Put expertise into tooling, not queues

The ask

"The technical competence to specify and support the building of these APIs is currently a scarce resource."

The decision

  • A paved road: a shared service kit gives every service the same pipeline, errors and config.
  • Types, validation and contract tests come from the contract, so mistakes fail in CI instead of waiting for a senior's review.
  • Seniors review contracts and improve the road instead of writing every API.

Adding an endpoint

  1. Write it in the contract
  2. Generate the types
  3. Add a handler named after the operation
  4. Run the contract tests

Four steps a less experienced developer can follow alone.

In the case Every service is built on packages/service-kit, and Schemathesis checks every response against its contract.

Hiring alone doesn't solve scarce expertise; encoding it does. The expert's judgement goes into the contract conventions, the kit and the checks, and every developer gets it for free. A rotating contract reviewer spreads the skill further.

Principle 5

Keep each rule in one place

The ask

"We want frontend and backend work to happen smoothly and in parallel."

The decision

  • Domain services own the business rules and their data.
  • A BFF only shapes that data into Screens, so a Screen change never touches the domain.
  • The server tells the app what the User may do, so rules are never copied into the app.

In the case A BFF over Identity, Card and Billing (ADR 0001); actions decides if "Activate card" shows.

Separate contracts per service mean separate streams of work. The cost is more network hops and more contracts; the gain is that Screen changes, which are frequent, never touch domain code, and domain changes never break the app's shape.

An App BFF over three domain services

The BFF holds no domain rules, and the Card API depends on no other service. The cost is more hops and more contracts; the gain is Screen changes that never touch the domain, and separate contracts to work on in parallel. (ADR 0001)

Each service owns its data and its database. The Card API is on the busiest path (the Card processor records purchases), so it must not wait on Identity or Billing. The BFF is where use-case concerns live: which Company is selected, how many Transactions to show, which buttons appear.

Payload decisions, made for the app

  • One round trip. The BFF calls the services in parallel on a fast network, so the phone makes one call on a slow one.
  • Money as integer minor units plus currency. No floats, and formatting stays on the client.
  • The server decides the buttons. actions lists what the User can do now, so lifecycle rules are never copied into the app.
  • Counts come ready. moreCount is "54 more", and remaining is never below zero.
  • Partial failure is explicit. If spend, transactions or the invoice fail, that section is null and listed in unavailable. The app shows it as loading, never as empty.
  • Only the essentials are required. If the Company list or the Card is missing, the answer is 502.
  • Writes return the Screen. PUT /cards/{id} answers with the refreshed Screen, so there's no second call.
  • No card numbers. Only last4. A full PAN belongs in the processor's secure view.
The distinction between null-because-none and null-because-unavailable matters on a finance screen: "no invoice due" and "we couldn't check your invoices" must never look the same.

Database: one per service, rules in the schema

-- card database
cards(id, company_id, holder_user_id, last4,
      expiry_month, expiry_year, expires_at,
      currency, spending_limit bigint,
      status -- inactive | active | frozen | closed
      closed_reason, created_at, updated_at)
  CHECK ((status = 'closed') = (closed_reason IS NOT NULL))
  UNIQUE (company_id, holder_user_id)
    WHERE status <> 'closed'      -- one open Card

transactions(id, card_id, amount bigint, currency,
             merchant_name, occurred_at, status)
  INDEX (card_id, occurred_at, id)
    INCLUDE (amount, status)

-- identity  users, companies,
            memberships(user_id, company_id)
-- billing   invoices(company_id, amount,
            due_date, due_at, status)
  • Integrity lives in Postgres: CHECK constraints on status, amounts and last4, and a partial unique index for "at most one open Card".
  • One index, two queries. The spend sum per card and month is an index-only scan, and newest-first paging uses the same index.
  • Time-based states are derived on read. expired comes from expires_at and overdue from due_at, so they're never stale.
  • No cross-database foreign keys. Services refer to each other by ID only.
Remaining spend is computed, not stored: a stored balance would need to be kept in step with every Transaction status change. The covering index makes the computed version cheap. Verifying that with EXPLAIN ANALYZE on a bulk seed is listed in further work.

Two rules that matter most

Remaining spend

Spending limit minus pending and settled Transactions in the current UTC month, never below zero.

// Card API, when the processor records a purchase
db.transaction().execute(async (tx) => {
  const row = await tx.selectFrom("cards")….forUpdate()
  const spent = await spentBetween(tx, row.id, period)
  if (spent + amount > row.spendingLimit) throw 422
  return tx.insertInto("transactions")…
})

The row lock serialises purchases on one Card, so two concurrent purchases can't together exceed the limit. The Screen and the check use the same month (ADR 0005).

Card lifecycle

UTC months are a trade-off: the purchase path carries no Company context, and fetching the Company's time zone would add a runtime dependency on Identity. A purchase in the first hour or two of a Swedish month counts towards the previous month. The fix (Company time zones replicated through events) is in further work.

Changing a Card: PUT with If-Match

PUT /cards/{cardId}
If-Match: "c2a9f0"        ← etag from the Screen
{ "status": "active" }

200  the refreshed Screen
428  If-Match missing
412  Card changed since you read it: reload
409  not allowed from this status
     + allowedTransitions
400  anything the contract doesn't allow
  • Why PUT: it's idempotent, so a retry on a flaky mobile network is safe. The full representation is validated as one object.
  • Why If-Match: it closes PUT's lost-update gap. The ETag is a hash of the canonical JSON (RFC 8785) of the Card, so it changes exactly when what a client sees changes.
  • The server derives the transition by comparing the current and requested status, so no transition logic lives in the client.
  • Upgrade path: POST /cards/{id}/activations once transitions need their own input or an audit trail. (ADR 0002)
The BFF forwards 404, 409 and 412 from the Card API as problem+json, and anything else from upstream becomes 502. All errors are RFC 9457 problem+json.

  • packages/service-kit is the paved road from the first half, as code.
  • Handlers stay thin. Rules live in pure domain/ functions with unit tests.
  • Kysely for type-safe SQL, with database types generated from the migrated schema.
  • Config is validated against a JSON schema at startup, so a bad environment fails fast.
  • Known cut: no authentication. A fixed demo User stands in, and the middleware is where a verified JWT would go (ADR 0003, 0006).

The BFF: as parallel as the data allows

  • Invoices depend only on the Company, so they load while the Card is still being found.
  • assembleCardOverview has no I/O and is unit tested. The handler only does the fetching.
handlers.ts orchestrates and screen.ts shapes. The BFF's clients are generated from the upstream contracts with openapi-fetch, so a contract change in the Card API shows up as a type error in the BFF.
