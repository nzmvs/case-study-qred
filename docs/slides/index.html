From the scenario to an architecture

Reading Qred's seven scenario statements, deriving the principles they imply, and the target architecture those principles lead to.

Nazim Huseynov · Node.js Backend Developer case

The approach: take the scenario at face value, group what it says, derive constraints, and let the architecture follow. The card overview implementation is the proof; details are in the appendix.

What the scenario says

  1. Qred's developers are required to build new APIs consistently to achieve specific business objectives.
  2. The technical competence to specify and support the building of these APIs is currently a scarce resource, and this slows us down.
  3. The mobile view in Appendix 1 is a frontend view in the mobile app which lacks an API implementation in the backend.
  4. The API definition and implementation sometimes occur too late in the software development lifecycle.
  5. Product Managers only have limited technical knowledge and require assistance in describing the technical implementation details for less experienced developers.
  6. The Frontend Developers are competent and can be frustrated by delays in API availability.
  7. We want frontend and backend work to happen smoothly and in parallel.

What it tells us

1The platform must keep changing with the business without breaking what exists. Composability is the trait we want.
2Knowledge is siloed. Few people understand the platform as a whole.
3The view spans three domains, and there is no single place the app team can get its data from.
4APIs get built before producer and consumer agree. Work turns waterfall, and documentation is dropped.
5Work is underspecified: PMs can't describe it, and developers can't infer it.
6One team's delivery depends on another's, so a delay upstream stalls the whole chain.
7Parallel work needs the work split at a clear interface boundary.
On 3: it's ambiguous whether the domains or only the composition is missing. Either way the app team would today need three subject matter experts (Identity, Card, Billing) to build one Screen.

Principle 1

Evolve by composition

From the scenario 1

The platform keeps changing to meet new business objectives, and no change may break existing products.

The constraint

New capabilities combine existing ones, and never break a consumer.

Leads to

  • Domain services with clear ownership
  • Additive, backward-compatible contract changes

In the demo The card overview composes the Identity, Card and Billing APIs without changing any of them.

Composability is what reconciles speed with stability: change happens by adding compositions, not by editing what consumers already depend on. It's also what makes experiments cheap, which comes back under innovation.

Principle 2

One front door per experience

From the scenario 32

The view spans three domains. Without one place to go, the app team needs three subject matter experts to build one Screen.

The constraint

A client gets everything a view needs from one place, under one contract.

Leads to

  • A BFF with one contract per Screen
  • Domain knowledge stays inside each domain

In the demo GET /screens/card-overview returns the whole view in one call. The app knows no other API.

The BFF shapes data and holds no domain rules (ADR 0001). That's what keeps a Screen change from ever touching a domain, and what lets the three domains be new, existing or mocked without the app caring.

Principle 3

Contract before code

From the scenario 45

APIs are built before producer and consumer agree, so work bounces back and forth.

The constraint

Nothing is built until producer and consumer agree the contract.

Leads to

  • An OpenAPI contract as the single source of truth
  • Code on day one: types, clients, validation, mocks and tests generated from it
  • Examples a PM can check against the design
  • Documentation as a by-product, never dropped

In the demo pnpm gen turns the contracts into types and typed clients; routes, validation and mocks come from the same files.

Two readings of "too late": product decides before feasibility is known, or the server is built without knowing how it's consumed. Getting everyone in the room over the contract fixes both: feasibility is checked there, and the consumer shapes it. And agreeing it pays off immediately in code: the moment it merges, both sides have generated types, clients, validation, a mock and tests to build on. It is not documentation written for later.

Principle 4

Knowledge is encoded, not siloed

From the scenario 25

Few people see the whole platform, and less experienced developers need the details spelled out.

The constraint

Specifying or building an API doesn't depend on a few people.

Leads to

  • Staff engineers with cross-domain responsibility, who own the primitives
  • Contract tests as the definition of done

Encoded as primitives

  • Shared shapes: one Money and one error format in every contract
  • A glossary: one word per concept, in contracts, code and conversation
  • Explicit rules: the card lifecycle as a published state machine
  • Internal tools and SDKs: shared packages that decide how a service is built
  • Lint rules: conventions checked, not remembered

In the demo An internal SDK under every service (packages/service-kit), the CONTEXT.md glossary, and contract tests.

The staff engineer is the owner of the primitives, not the bottleneck: their judgement goes into the tools, and they support initiatives by improving those tools rather than by being consulted on every project.

Principle 5

Every team ships independently

From the scenario 67

Frontend depends on backend's delivery, so a delay upstream stalls the whole chain, and backend is pushed to reprioritise.

The constraint

A team's deliverable depends only on what that team controls.

Leads to

  • Mocks generated from the contract
  • The contract as the only coordination point
Frontend deliversThe complete app, aware of every data source, built against the mock
Backend deliversThe workflows and data behind it, in its own time
They shareOnly the contract

Each roadmap is planned on its own, and blockers stay inside the team that owns them.

In the demo Prism serves every contract as a mock, so the app can be built before any service exists.

Principle 6

Integration is a switch

From the scenario 67

Once both sides are done, bringing them together must not become a project of its own.

The constraint

Mock to real is configuration, and never touches the app.

Leads to

  • A feature flag per upstream, in the BFF
  • The app always calls one stable API
  • No app release to switch, roll out or roll back

In the demo An Unleash flag per upstream, and a Qred-Data-Sources header naming what served each response.

The flags live in the BFF, not the app, because mobile releases are slow: the app stays stable and calls one API. Switching per upstream means Card can be real while Billing is still a mock, and real data can go to testers first. An unknown flag means real, and production never allows mocks (ADR 0004).

The target architecture

Contracts are knowledge "How do I cancel a Card?" PUT /cards/{cardId}  "Where do I get the User?" GET /me

The contracts carry both 3 and 4: besides being agreed first, they are the platform's knowledge in readable form. Questions that used to need a subject matter expert are answered by reading a contract. Every box answers a principle. This is exactly what runs in the demo: the three domain services, their contracts and mocks, the BFF with a flag per upstream, and the internal SDK underneath.

From mock to production

Today the real contract is discovered through round trips. Contract first agrees it once, the mock exists the same day, both sides build in parallel, and integration is a flag flip in the BFF.

An App BFF over three domain services

The BFF holds no domain rules, and the Card API depends on no other service. The cost is more hops and more contracts; the gain is Screen changes that never touch the domain, and separate contracts to work on in parallel. (ADR 0001)

Each service owns its data and its database. The Card API is on the busiest path (the Card processor records purchases), so it must not wait on Identity or Billing. The BFF is where use-case concerns live: which Company is selected, how many Transactions to show, which buttons appear.

Card database: cards

-- card database
CREATE TABLE cards (
  id              uuid PRIMARY KEY,
  company_id      uuid NOT NULL,
  holder_user_id  uuid NOT NULL,
  last4           char(4) NOT NULL CHECK (last4 ~ '^[0-9]{4}$'),
  expiry_month    smallint NOT NULL CHECK (expiry_month BETWEEN 1 AND 12),
  expiry_year     smallint NOT NULL,
  expires_at      timestamptz NOT NULL,
  currency        char(3) NOT NULL,
  spending_limit  bigint NOT NULL CHECK (spending_limit >= 0),
  status          text NOT NULL
                  CHECK (status IN ('inactive', 'active', 'frozen', 'closed')),
  closed_reason   text
                  CHECK (closed_reason IN ('lost', 'stolen', 'cancelled')),
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT cards_closed_reason_iff_closed
    CHECK ((status = 'closed') = (closed_reason IS NOT NULL))
);

CREATE UNIQUE INDEX cards_one_open_per_holder
  ON cards (company_id, holder_user_id) WHERE status <> 'closed';
CREATE INDEX cards_company_holder_idx
  ON cards (company_id, holder_user_id, created_at);
  • Statuses are text with a CHECK on the column, not ENUM types.
  • A closed Card always has a reason, and only a closed one does.
  • At most one open Card per holder and Company, through a partial unique index.
  • expired is derived from expires_at on read and never stored.
  • Money is integer minor units (bigint) with its currency.
Generated from apps/card-api/src/db/migrations (0001 and 0002) by Kysely's Postgres compiler. The lookup index exists because listCards filters statuses after reading (expired is derived), so the partial unique index never serves that query.

Card database: transactions

-- card database
CREATE TABLE transactions (
  id             uuid PRIMARY KEY,
  card_id        uuid NOT NULL REFERENCES cards (id),
  amount         bigint NOT NULL CHECK (amount > 0),
  currency       char(3) NOT NULL,
  merchant_name  text NOT NULL,
  occurred_at    timestamptz NOT NULL,
  status         text NOT NULL
                 CHECK (status IN ('pending', 'settled', 'reversed')),
  created_at     timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX transactions_card_occurred_idx
  ON transactions (card_id, occurred_at, id)
  INCLUDE (amount, status);
  • One index, two queries. The spend sum per Card and month is an index-only scan, and newest-first paging uses the same index.
  • Remaining spend is computed, not stored: pending and settled Transactions in the current UTC month.
  • Amounts are always positive. A reversal is a status, not a negative row.
A stored balance would have to be kept in step with every Transaction status change; the covering index makes the computed version cheap. EXPLAIN ANALYZE on a bulk seed is listed in further work.

Identity and Billing databases

-- identity database
CREATE TABLE users (
  id          uuid PRIMARY KEY,
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE companies (
  id          uuid PRIMARY KEY,
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE memberships (
  user_id     uuid NOT NULL REFERENCES users (id),
  company_id  uuid NOT NULL REFERENCES companies (id),
  created_at  timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT memberships_pkey
    PRIMARY KEY (user_id, company_id)
);
-- billing database
CREATE TABLE invoices (
  id          uuid PRIMARY KEY,
  company_id  uuid NOT NULL,
  amount      bigint NOT NULL CHECK (amount > 0),
  currency    char(3) NOT NULL,
  due_date    date NOT NULL,
  due_at      timestamptz NOT NULL,
  status      text NOT NULL
              CHECK (status IN ('open', 'paid')),
  issued_at   timestamptz NOT NULL
);

CREATE INDEX invoices_company_due_idx
  ON invoices (company_id, due_date);

One database per service Foreign keys only within a database. Across services, IDs only. overdue is derived from due_at.

due_at is the end of due_date in the Company's time zone, fixed when the Invoice is issued, so overdue can be derived exactly on read.
